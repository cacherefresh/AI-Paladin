Configuration manual

What you can change, where it lives, how to change it — and what each change costs you in protection. Every default in this manual is read from the files AI-Paladin ships with, version 0.1.0.

Three folders

Shipped defaults are read-only. Your settings live in your own folder. Logs live in a third. Nothing you change is lost on upgrade.

Changes are visible

Every start prints each file in force, where it came from and its checksum. Removing protection is printed as WEAKENED and written to the audit log.

Mistakes stop it, not you

A settings file that cannot be read as written stops the router from starting, rather than letting it run with rules you did not intend.

The rule

Never edit the shipped files to configure your install. Put your version in your settings folder. The shipped files are replaced on every upgrade; your folder is never touched.

The checksum (first 12 characters of SHA-256) lets you prove later which file was in force — the same line is printed at every start.

The demo keeps everything inside the repository so a demo machine leaves nothing behind in your home folder.

Protected terms · shipped defaults

Small and generic on purpose

A prompt — or any file it would carry — that matches a protected term runs on-prem, in every posture, before any socket opens. The shipped list covers what almost everyone protects. What is secret to your organisation, you add.

critical

Classification markings

classified · top secret · noforn · controlled unclassified
critical

Secrets & credentials

api_key · api key · secret_key · private key · password · credential · .env · bearer token
high

Customer data / PII

customer list · customer data · pii · ssn · social security · patient record · cardholder
medium

Internal infrastructure

internal.local · vpn config · prod database · kubeconfig

How matching works

Case-insensitive. A single word matches whole words only, so pii does not fire inside "happiness". Phrases match anywhere.

Beyond exact words

The sentry catches paraphrases ("our price calculation logic" for "pricing engine"); the misspelling gate catches "pricng engnie". Both can only add a match, never clear one.

The demo's terms

nightjar, pricing engine, unreleased earnings and the rest are not defaults. They live in the demo overlay, ai-org-router/config/keywords.yaml.

Protected terms · your overlay

Your keywords.yaml lists changes, not a copy

# ~/.config/ai-paladin/keywords.yaml

groups:                    # new groups, in full
  - group: projects
    label: Our projects
    severity: critical      # critical|high|medium|low
    terms: ["project falcon", "falcon-v2"]

add_terms:                 # extend any group
  credentials: ["vault token"]

add_paths:
  - "**/falcon/**"

remove_terms:              # removes protection
  credentials: ["password"]

remove_groups: []          # whole groups
remove_paths:  []
adds protection

groups, add_terms and add_paths only ever add. Duplicates are ignored, ignoring case.

removes protection

remove_terms, remove_groups and remove_paths are the only way to remove anything. Leaving a term out of your file removes nothing.

What the router prints when it starts

          WEAKENED  removed 'password' from credentials

The same removal is written to the audit log (topic rules.weakened) and returned by /api/config.

Protected terms · the rules

Five rules the overlay follows

1 · Updates still reach you

Your file holds only your changes. When a new version ships a new default term, you get it on upgrade — unless you named it under remove_terms.

2 · Removing is explicit

A shipped term or group goes away only when you name it. There is no "replace the whole list" switch for keywords.

3 · Removing is reported

Every removal is printed as WEAKENED at start, logged, and shown by the API. Removing something that is not there is a note, not an error.

4 · Mistakes stop the router

An unknown key, a group that does not exist, a list that is not a list, a bad severity, or YAML that does not parse: the router refuses to start and names the file.

5 · Reload is safe

Changed your file while the router runs? curl -X POST http://127.0.0.1:8722/api/reload, or restart. If the new file has a mistake, the previous rules stay in force and a critical notification says why.

New groups need a definition

A group you invent goes under groups with an id, label, severity and terms. add_terms can then extend it, like any shipped group.

Policy, roster, catalog · and the security rules

These are replaced whole

Put a policy.yaml, roster.yaml or catalog.yaml — or commands.yaml, packages.yaml, behavioral_rules.yaml (slide 14) — in your settings folder and it is used instead of the shipped one, all of it.

policy.yaml

Postures & internet

The four postures, the start-up posture and its lock, internet access, method switches, web limits, search engine, BIG-AI and pricing.

roster.yaml

Subagents

sentry (paraphrase gate), clerk (triage), engineer (on-prem execution), consultant (BIG-AI). Models, budgets, thresholds, the misspelling gate.

catalog.yaml

Models offered

Which models the picker shows, the default and fallback, and the licence allowlist.

How to start

$ mkdir -p ~/.config/ai-paladin
$ cp ai-org-router/router/policy.yaml ~/.config/ai-paladin/
# edit your copy, then restart
$ ai-paladin --where
  policy.yaml   user   1c0e9b2a77d4  ~/.config/ai-paladin/policy.yaml
the trade-off

Why whole files: a merge would let a missing or misspelt key silently change a security setting. A whole file is one thing to read and one checksum to record.

The cost: your copy does not receive improvements to the shipped file. After an upgrade, compare your copy with the new shipped one and carry over what you want.

Routing posture · policy.yaml · dashboard mode cards

Where unprotected work goes

Protected work always runs on-prem. The posture decides only what happens to work that does not match a protected term or path.

Pin the posture for an organisation

# ~/.config/ai-paladin/policy.yaml (your copy)
defaults:
  mode: sovereign
  lock_mode: sovereign   # mode bar greys out; API refuses others

Every change is audited

Each posture change is logged with who made it. Lifting sovereign is logged as critical. The sovereign guard covers the router's own process — not the rest of the machine. It is not a host firewall and not an air gap.

Most restrictive wins: sovereign forces no network; a task that matched a protected term is lowered from read/write to read-only; internet_access.lock pins the setting. Not saved: every restart starts at internet_access.default.

Limits · internet_access.limits

6 web calls per task · 600,000 bytes read per response · 5,000 characters handed back per call · 300-character queries · 4,000-character request bodies · 15 s timeout. Ports 80 and 443 on public addresses only — never loopback, the LAN or link-local.

Domain allowlist · internet_access.allow_domains

Empty (the default): any public website. List domains and only those — and their subdomains — can be reached; anything else is refused and logged. Include lite.duckduckgo.com or web search stops.

Everything the model sends out passes the protected-term gate. More than 3 refused requests in one task stop its web tools (fence-probing). TRACE, CONNECT, PRI can never be enabled.

On-prem model · catalog.yaml · dashboard model picker

Pick a model; AI-Paladin never downloads one

The picker

Choose the on-prem model in the dashboard. The choice is saved to local_models.yaml in your settings folder and survives restarts.

The catalog

catalog.yaml lists what the picker offers, the default (gpt-oss:20b) and the fallback (devstral-small-2).

The licence allowlist

Only models whose licence is on license_allowlist (Apache-2.0, MIT) can be selected. Others are shown, but greyed out.

downloading is egress

The router never pulls a model — that would be the router reaching the internet on its own. A model you have not installed is shown with the exact command for a person to run, outside the sovereign posture:

$ ollama pull gpt-oss:20b

Air-gapped machines

Pull on a connected machine, then copy ~/.ollama/models across. Ollama is a separate program: AI-Paladin does not install it, and its own network access is outside AI-Paladin's guard.

Web sign-in accounts · web_accounts.yaml

Secrets the model can use but never see

# ~/.config/ai-paladin/web_accounts.yaml
accounts:
  github:
    domains: [github.com]
    fields: {login: "...", password: "..."}
$ chmod 600 ~/.config/ai-paladin/web_accounts.yaml

How it is used

Only in READ/WRITE. The model names an account; the router fills the fields. The model never receives the values.

Bound to its domains

An account is only ever sent to a host on its own domains list. Asking to use it anywhere else is refused and logged.

Keep it private

If other users on the machine can read the file, the router prints a WARNING at every start until you chmod 600 it. The file is never committed: the demo's copy is gitignored.

Coding agents · security/policies · security/monitors

The Claude Code hook

These rules govern a coding agent: shell commands, file writes, package installs. They are enforced by a PreToolUse hook that Claude Code runs before every tool call — once you install it. Refused calls never run; the agent is told why.

RuleFileRefuses
Blocked commandscommands.yamlrm -rf /, curl … | bash, nc -l, history -c, encryption tools
Write scopecommands.yamlFile writes outside the project or into /etc, ~/.ssh, backups, .git/objects
Packagespackages.yamlInstalls not on the allowlist, unpinned, or from URLs / files
Credentialsbehavioral_rules.yamlReading or naming .ssh, .aws, .env
mass-file-touchbehavioral_rules.yamlWrites past 200 in 60 s
fence-probingbehavioral_rules.yamlEverything, after more than 3 refusals, until a person releases the session
hook-tamperbehavioral_rules.yamlThe agent switching the guard off: editing Claude's settings or AI-Paladin's config, --release, --uninstall
# a person turns it on and off - not the router
$ ai-paladin-hook --install          # this project
$ ai-paladin-hook --install --user   # every project
$ ai-paladin-hook --status
$ ai-paladin-hook --release SESSION_ID
$ ai-paladin uninstall             # removes it all

Independent of the router: stopping the router does not switch it off — otherwise that would be the way past every rule. Fails closed: if the hook cannot run at all, the call is refused and Claude Code shows how to recover (next slide). Every decision is written to hooks.jsonl in your log folder. Each rule's enforced: line in behavioral_rules.yaml says exactly what it covers. Full guide: ai-org-router/hooks/README.md.

Step by step

# run these in the project you want guarded
# 1. on - this project, or every project
$ ai-paladin-hook --install
$ ai-paladin-hook --install --user
#    start a new Claude Code session to pick it up

# 2. check
$ ai-paladin-hook --status

# 3. off, keep AI-Paladin - one project, or everywhere
$ ai-paladin-hook --uninstall
$ ai-paladin-hook --uninstall --all

# 4. remove AI-Paladin - hook everywhere first, then
#    the package. NOT a plain pip uninstall.
$ ai-paladin uninstall

Not installed with pip? Use the file by its full path, still from your project: python3 /path/to/AI-Paladin/ai-org-router/hooks/pre_tool_use.py --install

Where --install writes

This project: .claude/settings.local.json — personal, not committed. With --user: ~/.claude/settings.json — every project. Your other settings are kept, the old file is saved as .bak, installing twice never adds a second entry, and an unreadable settings file is left untouched.

order matters

Why not a plain pip uninstall?

pip runs nothing while removing a package, so it cannot take the hook out or warn you. A hook that cannot start refuses the call, so a leftover entry makes Claude Code refuse every tool call — its message names the file to fix. ai-paladin uninstall finds every recorded install, removes the hook from each, stops if any cannot be removed, then uninstalls (via pipx if that is how it was installed) and ends with an all-caps confirmation.

Already removed it? Recover from a terminal

Claude Code itself is blocked, so use an ordinary terminal in the guarded project: python3 /path/to/AI-Paladin/ai-org-router/hooks/pre_tool_use.py --uninstall (add --user if you installed it for every project). Folder gone too? Delete the pre_tool_use.py entry under hooks.PreToolUse in the settings file by hand.

Why stopping the router does not switch it off

If it did, stopping the router would be the way past every rule — and an agent can stop a process. The hook also refuses an agent that runs --uninstall or --release, edits Claude Code's settings or AI-Paladin's config, or runs pip uninstall ai-paladin (rule hook-tamper).

Honest limits · v0.1.0

What these settings do not do

The guard is process-level

The egress guard covers every connection the router's own process opens. It does not cover VS Code, your browser, Ollama or anything else on the machine. It is not a host firewall and not an air gap.

Single user, no sign-in

The router listens on 127.0.0.1 only and has no authentication. It is built for one person on one machine, not as a shared service.

The hook is a tripwire

It reads tool calls, not what a command does once it runs; variables and scripts can hide a command. Bash file writes are not scoped; package checksums, the approval queue and extension-rewrite detection are not enforced yet. Use a sandbox too.

BIG-AI is simulated

The cloud leg streams a labelled stub with modelled latency. The real adapter is not built yet.

No machine-wide lock yet

A user can change their own settings, including removing protection — visibly. An administrator layer that a user cannot weaken (/etc/ai-paladin/) is planned, not built.

Editable install only

ai-paladin runs from a source checkout today. PyPI, VS Code Marketplace and Ubuntu packages are planned; see DISTRIBUTION/.
